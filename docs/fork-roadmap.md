# WoWee fork: quality, completion, adoption and evaluation backlog

**Owner repository:** [mattes337/WoWee](https://github.com/mattes337/WoWee). **Created:** 2026-09-08.

Goal: make this fork the primary client, preserve WoWee's existing online and multi-expansion strengths, adopt demonstrably better behavior and algorithms from our Rust `wow-client`, and close the gaps in both implementations. The target is working original-client behavior, not just API registration, a visible panel, or successful packet decoding.

**Initial release target:** WotLK 3.3.5a/build 12340 on a controlled emulator. Preserve existing Classic/TBC/Turtle support through regression checks; certify those separately. Cataclysm is a later milestone. This is the full planning backlog within that scope, not a claim that every possible missing feature has already been discovered. Inventory and evaluation tasks below explicitly require adding newly found gaps.

**Testing approach:** use a real local emulator server for gameplay and multiplayer integration tests. A client-side sandbox/server replacement is out of scope. Keep automated input, assertions, screenshots, event/state checks, unit tests and small parser/widget fixtures. Those tests do not require implementing server behavior inside the client.

Implementation progress is recorded below with acceptance evidence. The initial evaluation remains historical; newer results supersede only the checks explicitly rerun. No fork changes have been pushed.

Evidence labels used below:

- **Gap:** a specific absent/default/approximate behavior was found in current code or an executed check.
- **Port:** a useful Rust implementation exists; preserve its behavior and adapt the boundary to C++.
- **Compare:** both have implementation; superiority must be demonstrated before replacement.
- **Validate:** functionality may exist, but its full acceptance scenario is unverified. This does not mean the feature is absent.
- **Dependency:** requires an identified server, data set, platform, or external service.

Priorities: **P0** establishes a trustworthy build/evaluation/test baseline; **P1** fixes everyday UI/gameplay and compatibility; **P2** completes advanced features and robustness; **P3** covers later versions and service-dependent extensions. Each task's **Done** clause is its acceptance gate. A task requiring implementation must include a regression that fails on the old behavior.

- [ ] **BASE-01 · P0 · Freeze donor evidence before each port.** Record donor commit, local diff or isolated source snapshot, source symbols, test inputs and relevant notices. Resolve any in-flight changes with the actual latest tree; the earlier renderer compile failure is a dated observation, not a permanent donor characteristic. **Done:** each port has reproducible source provenance, and unrelated local changes remain intact.
- [ ] **BASE-02 · P0 · Maintain one capability ledger.** For each system record client version, server revision, API/packet/data coverage, scenario, result, limitations and evidence path. Generate entries from registered APIs, no-op methods, missing-global logs, dispatch/skip handlers, CVars, widgets and test manifests; review false positives. **Done:** no item is called complete solely because a function exists, and every actual missing feature has an ID here or in a linked child task.
- [ ] **BASE-03 · P0 · Keep commits small and independently usable upstream.** Each commit should contain one coherent fix or improvement, its relevant regression test, and a short explanation of the behavior changed and validation performed. Keep unrelated cleanup, formatting, build changes and feature work in separate commits. Every commit must build and pass its affected tests. Where a change requires a series, state the dependencies and keep each step working. **Done:** the upstream maintainer can pull or cherry-pick individual changes without taking unrelated fork work.

Apply BASE-03 to every task below. A roadmap task may span several small commits; it is not a reason to bundle an entire subsystem into one commit. Keep changes compatible with upstream interfaces and defaults where possible, and isolate optional additions so the maintainer can choose what to take.
